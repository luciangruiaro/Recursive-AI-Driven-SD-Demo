# Group & Commit

Take the current uncommitted local changes and land them as a clean
sequence of small, logical commits. One concern per commit. No push.

## Hard rules

1. **Never push.** Only `git commit` locally. If the user explicitly asks to push, do it as a separate confirmed step.
2. **Never amend an existing remote commit.** Always create new commits.
3. **No AI/human attribution.** Do NOT include any of the following in commit messages:
   - `Co-Authored-By: Claude ...`
   - `🤖 Generated with [Claude Code]`
   - "Generated by ...", "Authored by AI ...", or any similar trailer
4. **No `--no-verify`** unless the user explicitly asks. If a hook fails, fix the underlying issue and try again.
5. **No `git add .` or `git add -A`.** Stage explicit paths so unintended changes (secrets, scratch files) cannot leak in.
6. **Always reset between groups if needed.** If a previous `git mv` / `git rm` left things staged, run `git reset HEAD` once before staging Group 1 so each commit only contains what the user expects.

## Procedure

### 1. Survey

Run these in parallel:

```bash
git status --short
git diff --stat
git log --oneline -5
```

Read the full diff for any file you don't recognize. Note for each
changed file: which logical concern it belongs to.

### 2. Group

Cluster files by **intent**, not by directory. Each group should be a
single sentence answer to "what does this commit do?". Common groups:

| Intent | Typical files |
|---|---|
| Deployment / containers | `Dockerfile*`, `docker-compose*.yml`, `scripts/docker/`, `.env.example` |
| CI / tooling | `.github/`, `.gitlab-ci.yml`, build/test config files (`pyproject.toml`, `package.json`, `Cargo.toml`, etc.) |
| Hygiene / ignore | `.gitignore`, `.dockerignore`, `.editorconfig`, `.pre-commit-config.yaml` |
| Docs reorg | `docs/`, root-level `*.md` moves |
| Security hardening | entrypoints, secret guards, auth code |
| Script / folder reorg | `git mv` chains under `scripts/`, `tests/` |
| Cross-reference fixes | follow-up edits triggered by a previous group's moves |
| Feature change | source files implementing one user-visible behavior |
| Bug fix | source files closing one regression |
| Refactor | structural change with no behavior change |

**Rules of thumb:**
- A file edit that exists *because of* another change in this batch (e.g. updating a path comment after a `git mv`) belongs in the same commit as the move it's reacting to. Same intent.
- If two unrelated hunks live in the same file, split them. Either with `git add -p` (manually), or by **temporarily reverting** the second hunk, committing the first, then re-applying the second for the next commit.
- Aim for 3–8 commits for a typical batch. If you're producing 12, you're slicing too thin. If you're producing 1, you're not slicing.

### 3. Stage cleanly

For each group:

```bash
git reset HEAD                    # only the FIRST time, to clear stale staging
git add <explicit paths>          # never -A or .
git status --short | grep '^[AMDR]'  # verify only intended files are staged
```

For renames: stage **both** the old and new path so git records it as a rename, e.g.
```bash
git add OLD.md docs/new.md
```

### 4. Commit

Use a HEREDOC for the message:

```bash
git commit -m "$(cat <<'EOF'
<scope>: <imperative summary, lowercase, ≤72 chars>

<optional body — only if needed for non-obvious detail>
- bullet 1
- bullet 2
EOF
)"
```

**Message style:**
- **Subject line**: `<scope>: <imperative verb phrase>`. `<scope>` is one of `docker`, `docs`, `chore`, `scripts`, `tests`, `ci`, `feat`, `fix`, `refactor`. Keep ≤72 chars. No trailing period.
- **Body**: omit if the subject says enough. If you do write one, use bullets for multi-thing commits, prose for single-concern detail. State *what* and *why*, never *how*.
- **No emojis** unless the user explicitly asks.
- **No mention** of AI, "Claude", "Generated with...", "Co-Authored-By", or similar.

### 5. Verify between commits

After each `git commit`:

```bash
git status --short                # confirm only the next group is left
git log --oneline -1              # confirm the message looks right
```

If a hook (pre-commit, lint, test) fails: fix the issue, **re-stage**, create a **new** commit. Never `--amend` to bypass.

### 6. Final check

When the working tree is clean:

```bash
git status                        # "nothing to commit, working tree clean"
git log --oneline -<N>            # show the N commits you just made
```

Surface the commit list to the user as the final summary.

## Anti-patterns

- ❌ One giant commit "fix everything"
- ❌ `git add -A` followed by `git commit -m "wip"`
- ❌ Commit messages like "various improvements", "stuff", "wip", "minor fixes"
- ❌ Mixing a refactor with a behavior change in the same commit
- ❌ Pushing without explicit user request
- ❌ Skipping hooks with `--no-verify`
- ❌ AI/human attribution trailers (Co-Authored-By, "Generated with...")

## Worked example (reference)

A batch with these pending changes:
- container build files + dev iteration helpers (deployment)
- entrypoint hardening (secret guard)
- `.dockerignore`, `.gitignore` (hygiene)
- a handful of doc files moved into `docs/` (docs reorg)
- build config consolidation across multiple files (tooling)
- script folder reorganisation + cross-ref edits in 5 files

Splits into:

1. `docker: add multi-tenant build profiles and dev iteration helpers`
2. `docker: refuse to start with default secrets`
3. `chore: audit .dockerignore and .gitignore`
4. `docs: move loose root docs to docs/`
5. `chore: consolidate build tooling config`
6. `scripts: regroup tools by integration; add host-services and tests/smoke`

Six commits, each readable on its own, each leaves the tree compilable, no push.
